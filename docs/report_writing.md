# SRC 报告写作指南（怎么写才被采纳）

> SRC 评审每天看几百份报告，**写得清楚 = 通过率高，写不清楚 = 被忽略/拒绝**。
> 核心：评审能 3 分钟内复现你的漏洞，并判断危害。

## 一、报告结构（平台通用）

    标题：一句话说清漏洞（类型 + 位置 + 危害）

    1. 漏洞概述（2-3 句）
    2. 复现步骤（可重现！）
    3. 影响分析（危害量化）
    4. 修复建议

## 二、标题写法

    好的：某站点订单接口存在水平越权，可查看任意用户订单（含手机号）
    差的：发现一个漏洞 / SQL注入 / IDOR

要点：**类型 + 具体接口 + 最严重危害**。评审按标题快速分类。

## 三、复现步骤（决定生死）

必须让评审**照着做就能复现**：

    1. 注册两个账号 A、B（测试用）
    2. 用 A 登录，获取 cookie
    3. 请求：GET /api/order?id=1002 （带上 A 的 cookie）
    4. 响应：返回了 B 的订单（id=1002 属于账号 B）：
       响应体截图（关键字段打码）

三个硬要求：
- **带认证信息**（cookie/token 怎么来的要写清）
- **贴原始请求/响应**（或至少关键部分），不是描述
- **截图/证据**：响应体差异对比图（A 看 B 数据 vs B 自己看）

## 四、影响分析（危害量化）

按"能造成什么损失"写，不写"存在风险"这种空话：

    好的：攻击者可越权读取任意用户订单（含姓名/手机号/地址），
         涉及个人敏感信息泄露，且订单号可枚举，影响全部用户
    差的：存在越权风险

不同漏洞的影响参考：
- IDOR：能读哪些数据 → 敏感程度
- SQLi：能读库 / 能写 / 能 RCE
- 存储 XSS：管理员会话窃取 → 账号接管
- SSRF：云元数据凭据 → 内网横向

## 五、红线（违规直接封号）

1. **严禁拖库/下载真实用户数据**：证明到 version()/database() 即可
2. **严禁 DoS/爆破/撞库**：批量测试也不行
3. **严禁未授权目标**：严格在 scope 内
4. **数据打码**：截图里的真实手机号/身份证必须打码
5. **别测试第三方**：不要因你的测试影响无关系统

## 六、常见被拒原因

| 原因 | 对策 |
|---|---|
| 复现步骤不完整 | 从零开始写，含登录、cookie、每一步请求 |
| 危害说不清 | 量化：能读什么、影响多少人 |
| 漏洞不存在/误报 | 用工具验证层（负对照/交叉验证）确认后再报 |
| 反射 XSS（低价值） | 除非能证明存储/管理员触发，否则别报 |
| 报告过长 | 控制在 1 屏能读完，证据放附件 |

## 八、提交前自检清单

- [ ] 复现步骤从零可重现？
- [ ] 请求/响应贴了原始数据（脱敏后）？
- [ ] 影响量化了（能读什么/影响多少人）？
- [ ] 截图关键字段打码？
- [ ] 修复建议针对该技术栈？
- [ ] 目标在 scope 内？
